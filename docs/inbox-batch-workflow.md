# 英语伴读：合集输入与动态规划流程

## 目的

把一份包含多篇英文原文的 Markdown 合集，稳定地转化为逐篇独立、可核对的英语伴读稿。流程以本地文件为唯一事实来源：得到笔记负责高质量文字识别；ChatGPT 在明确边界内规划和执行伴读任务。

## 输入、输出与职责

| 环节 | 责任方 | 输入或动作 | 完成标志 |
| --- | --- | --- | --- |
| 原文识别 | 用户、得到笔记 | 将 PDF 原文按篇截图；得到笔记识别为 Markdown | 得到一份包含独立原文篇章的 Markdown 合集 |
| 任务交接 | 用户 | 将合集放入 `content/inbox/` | 文件进入待处理队列 |
| 动态规划 | ChatGPT | 识别合集中的文章边界、编号、标题、作者和正文；检查目标冲突 | 形成可执行的逐篇处理计划 |
| 内容生产 | ChatGPT、英语伴读技能 | 为每篇建立权威原文并生成伴读稿 | `sources/` 与 `readings/` 中各有一份对应文件 |
| 逐篇验证 | ChatGPT | 校验原文、元数据、结构、引用原文一致性和文件路径 | 该篇通过直接校验 |
| 归档 | ChatGPT | 仅在合集中的全部篇章均通过后移动输入文件 | 合集位于 `content/processed/` |

## 目录状态

```text
content/inbox/      待处理的 Markdown 合集
content/sources/    从合集拆出的权威单篇原文
content/readings/   与单篇原文一一对应的伴读稿
content/processed/  已完成全部派生文章并通过校验的原始合集
```

一个 `inbox` 文件是一个输入包，不是强制的执行批量。例如，它可以包含十篇独立原文，用于统计；ChatGPT 应根据文章的完整度、独立性和冲突风险规划实际处理顺序，而不是按固定篇数机械分组。

## ChatGPT 的动态规划契约

收到“处理 inbox”或等效任务后，ChatGPT 应：

1. 只发现 `content/inbox/` 中待处理的 Markdown 文件，忽略系统文件和非原文文件。
2. 将每个合集解析为独立文章，识别文章编号、标题、作者（如有）和正文边界。
3. 将可明确识别的文章排入队列；若编号、标题、正文边界不清，或目标文件已存在，则将该篇标为待确认，不得猜测、覆盖或静默跳过。
4. 按文章独立性、文本完整度和文件冲突风险安排处理顺序；不以输入包中的文章数量作为拆分规则。
5. 为每篇新 HONY 文章保存 `content/sources/HONY-NNN-english-slug.md`，再按照当前 `english-reading-companion` 技能生成同名的 `content/readings/HONY-NNN-english-slug.md`；`NNN` 从 `001` 起连续编号，直到新规则出现。
6. 每完成一篇立即进行直接校验；失败的文章不应被计为完成。
7. 只有输入包中的所有文章都完成并通过校验时，才将原始合集从 `content/inbox/` 移至 `content/processed/`。

## 单篇完成条件

一篇文章只有同时满足以下条件，才算完成：

- 原文已保存到 `content/sources/`，且编号、标题、作者、拼写、标点和段落与权威输入一致；
- 伴读稿已保存到 `content/readings/`，且不覆盖既有文件；
- 伴读稿使用当前技能版本，并具有规定的隐藏元数据和 `draft` 状态；
- 伴读稿覆盖 Story、Language、Thinking、Beyond the Words 四层，并显示完整的 `Original Text / 对照原文`；
- 对照原文与保存的单篇原文一致，且文件路径、命名和 Markdown 基本结构有效。

## 收尾与汇报

每次处理完成后，仅汇报：输入包名称、识别篇数、完成篇数、待确认篇数及原因、通过校验的产物路径，以及输入包是否已归档。未通过校验或待确认的输入包必须保留在 `content/inbox/`。

## 观察性试运行

下一份真实合集进入 `content/inbox/` 后，先按本流程运行一次，不修改技能。记录：识别篇数、待确认原因、实际处理顺序、每篇校验结果和总耗时。一次运行只能提供改进候选；只有在不同输入包中重复出现的模式，才考虑固化进技能或自动化检查。
